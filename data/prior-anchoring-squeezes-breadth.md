# anti: 錨定成本擠壓覆蓋廣度(加錨要求後作者寫得更準但寫得更少)

**op/iter**:前科,非本 op —— 2026-07-05 `superpowers@v6.1.1` A/B run
(同 repo 同 pin 同模型,唯一變因＝claim contract + T0 pre-verifier)。
原始帳本 `kb-ingest/engine-baseline.md`(退役引擎,保留為實測證據);
退役決策 `.agents/skills/repo-wiki-converge/modules/official-port-map.md` §3–4。

**症狀**
- 捏造率 baseline → **0**(13 批獵殺零捏造,行號抽查 11/11 精準)。錨定機制本身有效,不是這條 anti 的爭點。
- **round-1 覆蓋 6 頁 → 3 頁**。帳本原文:「分數瓶頸從『髒』換成『窄』」。
- 總分 68 → 72(僅 +4);作者耗時 **+40%**。
- 三個假設全 FAIL:claim contract→round-1 ≥80 FAIL、pre-verifier→判官批次 −60% FAIL、輪數 ≤1+2 FAIL。

**根因**
錨定是**作者側的單位成本**:每個 claim 要回源碼找逐字證據。單位成本上升而預算不變 ⇒
作者自動用**縮小範圍**來吸收,而不是用更長的時間。這不是模型偷懶,是有界資源下的理性配置——
所以「叫它別縮範圍」沒有用,必須讓廣度變成**被獨立量測的硬約束**,或把錨定移出生成的關鍵路徑。

**禁回退**
1. **禁在沒有覆蓋率硬門檻的情況下加錨要求。** 本 op 的凍結門檻 3(entrypoint 覆蓋 ≥93.8%,
   即 baseline 實測值)就是這條防線,不得下調——這正是帳本建議的「page-budget 下限」。
2. **禁用重跑 `init` 的方式加錨。** 帳本建議的是「create 先廣後錨」。baseline 的 44 頁已經是
   「先廣」的成果(93.8% 覆蓋、三閘全過、0 壞鏈);重生會把它丟掉並重新承受一次廣度擠壓,
   而且讓 A/B 同時含「加錨」與「重擲生成骰子」兩個變因,+10pp 分不清是誰的功勞。
   ⇒ 走 `update` 模式對既有頁做錨定 pass,單一變因。
3. **禁只看錨定率宣告成功。** 錨定率上升同時覆蓋率下降 = 這條 anti 正在重演。
   兩個數字必須同時看,`audit_wiki.ts` 一次吐出兩者就是為了讓人無法只挑一個看。
4. **禁把「+40% 作者耗時」當可忽略。** 它在本 op 會轉成 token 成本與單頁 stop-loss 的壓力,
   是全局熔斷(降級頁 >5 中止)之外的第二個成本面。

**同時吸收的正面前科(來自退役 `verify-claims.sh` 本體,已讀碼)**
- 它的 **H4**:每個 `## Why` 段落的每一段必須帶 `(src: …)` 或 `(unverified)`。
  本 op 的 `(inferred)` 只是慣例、未強制 —— **門檻 6 的實作應採 H4 的段落級強制**,
  否則 C5 會靜默退化。
- 它的 **W1 裸檔名掃描是 advisory 不阻斷**,理由「runtime 路徑本來就不在樹裡」。
  本 op 實測 6 個 unresolvable 全是跨 repo 引用,獨立收斂到同一結論 —— 維持不當閘。
- 它的 **H2 只驗「路徑存在 ∧ 行號 ≤ EOF」,引文是分開的 H3 且只覆蓋 blockquote**,
  所以裸 `(src: path:88)` 在它底下合法 = hollow anchor 可過。
  本 op 的錨**內建強制引文**,不重蹈此缺口。
